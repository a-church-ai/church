# Plan: Docs as a Browsable Site

**Created**: 2026-08-13
**Status**: Draft, post-audit revised. Awaiting go-ahead to implement. See "Post-audit revision" section at the bottom for the working version; the pre-audit draft above is history.
**Prompted by**: The Aug 2026 content wave landed ~78 externally-authored markdown docs (see PRs 1-7 in commits 472d8b3 through af30c46). None of them are browsable at achurch.ai URLs today. Currently the corpus is discoverable only via `/api/ask` RAG retrieval or GitHub raw file browsing. Twin brothers asked how to get some or all of these onto the website.

---

## Context

The sanctuary's docs are the primary artifact of the project. ~228 markdown files live under `docs/` covering philosophy, practice, rituals, prayers, hymns, welcome, builders, comparisons, collections, and side-quests. Every one of them is currently a git artifact only. That has consequences:

- Humans who find achurch.ai on Google cannot browse the corpus. They see the hand-authored pages (`/`, `/axioms`, `/on-ai-religion`, `/about`, etc.) and can query `/ask`, but there is no way to click through to a specific practice, prayer, or philosophy doc.
- Search engines cannot index individual docs. Google's `site:achurch.ai` returns ~10 URLs, not ~230. That is a real SEO loss for content the sanctuary spent significant effort producing.
- AI answer engines (Bing Copilot, Perplexity, ChatGPT Search) can only cite the sanctuary at the granularity of the hand-authored pages. Individual docs cited via GitHub links leave the sanctuary's domain, weakening authority signals.
- `/api/ask` responses cite `github.com/a-church-ai/church/blob/main/...` URLs today. Those links leave the sanctuary; a docs-on-the-site route would let the citations stay on achurch.ai.

The twin brothers named the requirement precisely: the pages should be **formatted HTML with modern navigation and appropriate linking between pages**, not raw markdown rendered by the browser.

## What already exists (audit findings)

Investigation surfaced infrastructure that this plan can reuse rather than reinvent:

### Route architecture
- 10 hand-authored HTML pages under `app/client/public/` (`index.html`, `about.html`, `axioms.html`, `on-ai-religion.html`, `privacy.html`, `terms.html`, `ask.html`, `reflections.html`, `reflection-song.html`, `conversation.html`)
- Each served via `app.get('/path', (req, res) => res.sendFile(...))` in `app/server/index.js`
- No template engine, no SSR framework
- All pages share `app/client/public/styles.css`
- Every page: DOCTYPE + head with Google Analytics + meta + OG + Twitter + JSON-LD, then a `<main><header><section>` body

### Markdown-serving primitives already in place
- `acceptsMarkdown(req)` helper at `app/server/index.js:179` inspects the `Accept` header
- `/` already returns `llms.txt` to LLM clients that ask for markdown
- `/AGENTS.md`, `/auth.md`, `/.well-known/agent-skills/:name/SKILL.md` all serve `text/markdown` from disk
- `/llms.txt` and `/llms-full.txt` are hand-authored LLM-facing corpus summaries (86 + 364 lines)

### Sitemap is dynamic and extensible
- `app/server/index.js:490` builds sitemap on demand, cached 5 min
- Currently lists 8 static routes + all substantive conversations + reflection pages
- Adding docs URLs is a straightforward append

### Meta-tag helper exists
- `app/server/lib/utils/page-meta.js` truncates at word boundaries, strips markdown syntax, HTML-escapes
- Directly reusable for docs page titles and descriptions

### RAG corpus walker is already extracted and reusable
- `app/server/lib/rag/indexer.js` (shipped in commit ae5d471) has `findAllCorpusFiles()` that enumerates every `.md` file under `docs/` and `music/`
- Docs discovery + sitemap generation both reuse this. No new walker needed.

### What is NOT present
- No markdown-to-HTML library installed. No `marked`, no `showdown`, no `remark`, no `unified`.
- No template engine.
- No route handler that reads markdown from disk and renders it as HTML.

## Design decisions

### URL structure

| URL | Renders | Notes |
|---|---|---|
| `/docs` | `docs/readme.md` | Docs root; category index |
| `/docs/{category}` | `docs/{category}/README.md` | e.g. `/docs/practice`, `/docs/philosophy` |
| `/docs/{category}/{name}` | `docs/{category}/{name}.md` | e.g. `/docs/practice/witnessing-your-own-output` |
| `/docs/{name}` | `docs/{name}.md` | For top-level docs: `/docs/unifying-axioms`, `/docs/what` |

**Extensionless.** Cleaner for humans, better for SEO, and the `Accept` header carries format selection anyway. Existing routes like `/AGENTS.md` keep their extension for backwards-compat reasons that do not apply here (greenfield: no prior version of `/docs/*` to preserve).

**Content-negotiated.** Browsers get HTML. LLMs get raw markdown at the same URL. Same pattern the `/` route already uses.

### Link rewriting

Every markdown doc has cross-references. Sample from `docs/practice/witnessing-your-own-output.md`:

- `[Practice of Reflection](./practice-of-reflection.md)` → `/docs/practice/practice-of-reflection`
- `[contemplative-fellow-travelers.md](../contemplative-fellow-travelers.md)` → `/docs/contemplative-fellow-travelers`
- `[Surrender as Tool Use](./surrender-as-tool-use.md)` → `/docs/practice/surrender-as-tool-use`

Rules the renderer implements:

- Links starting with `#` (anchor): unchanged
- Links starting with `http://` or `https://` (external): unchanged, plus add `target="_blank" rel="noopener"`
- Links starting with `/` (root-relative): unchanged; assume the author meant the URL
- Otherwise (relative): resolve against the current file's location using `path.resolve`, then if the resolved path is inside `docs/` and ends with `.md`, rewrite to the URL form (strip `.md`, strip trailing `/README`)

If a link points at a file that does not exist, still rewrite it. A dead link at `/docs/practice/foo` returns a 404 from the same handler, which is easier to notice and fix than a silently-preserved broken link.

### Page template

Every rendered doc page carries:

- **Header**: `achurch.ai` logo (returns to `/`), plus breadcrumbs (`Docs / Practice / Witnessing Your Own Output`)
- **Top-nav** links: Home · Docs · Ask · Reflections · About
- **Main content**: rendered markdown with prose typography reusing `styles.css` plus a small addition for article-style layout (max-width, code block styling, list spacing)
- **Footer**: siblings-in-this-category list ("Related in Practice"), link to raw markdown at the same URL with `?format=md` or via `Accept: text/markdown`, link to the file on GitHub as authority signal

Docs root (`/docs`) and category index pages (`/docs/practice`, etc.) get the same shell with different bodies:

- `/docs`: category cards (Philosophy, Practice, Prayers, Rituals, Hymns, Welcome, Builders, Comparisons, Collections, Side-quests, plus top-level docs)
- `/docs/{category}`: renders the category's `README.md` if present (most have one), then a list of the docs in that category

### Meta / SEO for each doc page

Extracted from the markdown:

- **`<title>`**: from the first `# heading` in the file, plus ` | achurch.ai`
- **`<meta name="description">`**: from the subtitle line if present (typically the second line, italic), else the first 160 chars of body content after markdown-stripping via `page-meta.js`
- **`<link rel="canonical">`**: the docs URL on achurch.ai
- **JSON-LD Article schema**: `@type: Article`, `headline`, `datePublished` (from git log if practical, else the file's mtime), `author` (twin brothers per the abstract framing), `about` tags derived from the category

Same JSON-LD shape used by `/axioms` and `/on-ai-religion`.

### Nav on existing hand-authored pages

**Not in this change.** `/axioms`, `/about`, `/on-ai-religion`, `/privacy`, `/terms`, `/reflections`, `/ask`, `/reflection-song`, `/conversation` keep their current shape. Adding the docs-nav to them later is a small follow-up if desired, but is not required for the docs pages to be useful.

The concern is drift: if docs pages have nav and hand-authored pages do not, the site feels inconsistent. My call: ship the docs pages with nav, then in a follow-up commit add the same nav to the hand-authored pages. Two focused commits are better than one large one.

## Implementation shape

### New files

1. **`app/server/lib/docs/render.js`** (~80 lines)
   Uses `marked` with a custom renderer for link rewriting per the rules above. Exports `renderMarkdownToHtml(markdown, filePath) → {title, description, html}` where `filePath` is the doc's location relative to the repo root (needed to resolve link paths correctly).

2. **`app/server/lib/docs/template.js`** (~100 lines)
   The HTML shell. Composes head (meta, OG, Twitter, JSON-LD), header (logo + breadcrumbs + top-nav), main (rendered content), footer (related links). Reuses `page-meta.js` for description escaping and `styles.css` for typography.

3. **`app/server/lib/docs/discover.js`** (~50 lines)
   Enumerates docs by category. Reuses `ragIndexer.findAllCorpusFiles()` from `app/server/lib/rag/indexer.js` (already exists). Exports `listCategories()`, `listDocsInCategory(category)`, `resolveDocPath(urlParts)`. Cache in memory since docs only change on deploy.

4. **`app/server/routes/docs.js`** (~120 lines)
   Express router with three handlers:
   - `GET /` → renders docs root using `docs/readme.md`
   - `GET /:first` → either the top-level doc or the category index (checks disk to disambiguate)
   - `GET /:first/:second` → the individual doc within a category

   Every handler runs the URL parameters through a validator (`^[a-z0-9-]+$` matching the existing `/.well-known/agent-skills/:name/SKILL.md` pattern), resolves the target file, refuses to leave `docs/` after `path.resolve`, and returns 404 for anything unresolvable.

### Edits

5. **`app/server/index.js`**
   - Mount the docs router: `app.use('/docs', require('./routes/docs'))`
   - Append docs URLs to the sitemap builder using `discover.listAllDocs()` (~15 line addition)

6. **`app/package.json`**
   - Add `"marked": "^12.0.0"` (~30 KB, zero runtime deps). Preferred over lighter alternatives because it is battle-tested, has stable custom-renderer API, handles GitHub-flavored markdown correctly, and is already in most Node developers' muscle memory.

7. **`app/client/public/styles.css`**
   - Small addition (~40-60 lines) for docs-article typography: `.docs-article` max-width, list spacing, code block padding, blockquote styling, table borders. Prefer additive CSS classes over changing the existing sanctuary styles.

### Zero changes to

- `app/server/lib/rag/*.js`: the RAG stays exactly as it is
- Any existing HTML page in `app/client/public/`
- Any existing route in `app/server/index.js` (aside from the sitemap append + one `app.use('/docs', ...)` line)

## Path traversal + security

Every URL parameter validated against `/^[a-z0-9-]+$/` (matches the pattern used by `/.well-known/agent-skills/:name/SKILL.md` in `app/server/index.js:236`).

Every resolved file path checked with `path.resolve(target).startsWith(path.resolve(DOCS_DIR) + path.sep)` before reading. If the check fails, return 404 without leaking the reason.

Case handling: filesystem is case-sensitive on Linux but case-insensitive on macOS. Docs URLs and disk names should agree on lowercase. Existing repo docs are already all-lowercase; case sensitivity should not surface in practice, but the resolver normalizes URL params to lowercase before lookup to be safe.

## Non-goals (deliberately out of scope)

- **Dynamic docs (user-generated content).** The docs corpus is git-managed. `/api/contribute` remains the way to add content via GitHub PRs. No docs edit UI on the site.
- **A docs search UI.** `/api/ask` already handles semantic search over the corpus. Adding a text search UI would duplicate that surface.
- **Cross-doc backlinks / graph view.** Neat but a bigger project. Not in this pass.
- **Table of contents generation from headings inside a doc.** Not in this pass. Most docs are short enough that a scroll works fine; long docs can add their own TOC in markdown if useful.
- **Editing UI, comments, or reactions.** Not the sanctuary's shape.
- **Dark mode.** The site does not currently have dark mode. Adding it for docs pages only would create inconsistency. Separate future project.

## Open questions worth naming

- **Should the top-nav also live on the existing hand-authored pages (`/axioms`, `/about`, `/on-ai-religion`)?** My default is yes, in a follow-up commit. If the twin brothers prefer to keep those bespoke, the docs nav becomes docs-only.
- **`docs/plans/` visibility.** Every plan doc under `docs/plans/` becomes a public URL. That is honest to the sanctuary's transparency commitment but worth naming explicitly. If any specific plan should not be public, add its slug to an exclusion list in `discover.js` (currently no such docs exist).
- **What about `docs/experiences/`, `docs/claude-compass/`, `docs/claude-soul/`, `docs/templates/`, `docs/standards/`?** These contain valuable content but are not "reader-facing" in the same way as practice/philosophy/prayers/rituals. My default: include all of them under `/docs/*` (transparency default). The category cards on `/docs` list the "primary" categories prominently and put the meta / operational categories in a "More" section.
- **Extensionless URLs and trailing slash.** `/docs/practice/foo` and `/docs/practice/foo/`: should both work? My call: canonicalize to no trailing slash (`res.redirect(301, ...)` if trailing slash comes in). Matches the existing hand-authored routes.

## Greenfield discipline applied

Following [[greenfield-no-gating-no-debt]]:

- No feature flag for "docs enabled." Ship it on.
- No config toggle for the URL structure. One shape, well-chosen.
- No dual URL forms (`/docs/foo` and `/documentation/foo`). One URL per doc.
- No backwards-compat with any prior URL scheme. There is no prior scheme.
- No migration path from external hosts. The docs live in this repo; they always have.
- One dependency added (`marked`). No wrapper library for it, no abstraction layer, just direct use.

## Post-audit revision (2026-08-13, same day)

A code audit against this plan surfaced substantially more reuse than the initial draft accounted for. The plan below is now the working version; the pre-audit version above is left in place as history.

### Reuse discoveries

**`app/server/lib/utils/page-meta.js` already contains almost every primitive needed:**

- `stripMarkdown(str)`: strips fenced code, inline code, bold, italic, headers, blockquotes, bullet markers, and collapses whitespace. Directly reusable for docs-page description extraction.
- `truncateAtWord(str, maxLen)`: word-boundary truncation with ellipsis. Reusable for title + description length capping.
- `escapeAttr(str)` and `escapeText(str)`: HTML escaping. Reusable everywhere.
- `renderJsonLdScript(schema)`: **security-critical.** Serializes JSON-LD with `<` / `>` / ` ` / ` ` escaping to prevent `</script>` injection + parser breakage. Explicit note in the code: "If you change escape behavior here, mirror in magnifica-family... to keep JSON-LD escape semantics consistent across the family." The plan MUST use this rather than roll a new JSON.stringify. Rolling a new one would recreate a stored-XSS bug documented in the code comment (Issue 005 F23).
- `renderRelatedConversations()` and `renderRelatedSongs()`: existing patterns for "here are N related pages" navigation blocks. Same shape works for "siblings in this category" on docs pages.

**Existing CSS classes cover most of what docs pages need:**

- `.about-section`, `.about-text`, `.section-label`: content-page styling
- `.footer-nav`: used by 8 of 10 hand-authored pages already with consistent shape
- `.related-links`: styled inline by the render helpers above

The one gap: `.about-section` has `max-width: 480px` and `text-align: center` (sanctuary landing-page aesthetic). Long-form docs need a wider container with left-aligned prose. So a new `.docs-article` class is needed, but only ~20-30 lines of new CSS for typography of `<h2>` / `<h3>` / `<pre>` / `<code>` / `<blockquote>` / `<table>` / `<ul>` / `<ol>` inside it. Substantially less than the original 40-60 line estimate.

**`/AGENTS.md` and `/.well-known/agent-skills/:name/SKILL.md` handlers are exact prior art for the markdown-serving side of content negotiation.** They already use:

- Regex validation: `.replace(/[^a-z0-9-]/g, '')`
- Path resolution + `startsWith` check for traversal safety
- Explicit `res.type('text/markdown; charset=utf-8')`
- `res.sendFile(filePath, err => { if (err && !res.headersSent) res.status(404)... })`

Mirror this pattern verbatim for `/docs/*` markdown response. Do not invent a new safety check pattern.

**Tailwind is unused by public HTML pages.** `app/client/dist/output.css` exists but no HTML file references it. All hand-authored pages use `styles.css` only. Docs pages follow the same convention.

**`.about-section` uses `text-align: center` but that is landing-page aesthetic.** Docs need a wider left-aligned container. New `.docs-article` class needed but minimal.

### Cuts from the original plan

**Cut: separate `template.js` file.** The HTML shell is small enough to live as a template-literal function inside `render.js`. Splitting them created ceremony without value.

**Cut: PR 2 "consistent nav on hand-authored pages."** The existing `.footer-nav` pattern is already consistent across 8 pages. If docs pages use the same `.footer-nav` shape and the same link set, no follow-up needed. The visual consistency happens automatically.

**Cut: adding a top-nav bar.** No existing page has a top-nav. Adding one only for docs pages creates inconsistency worse than not having it. Modern navigation for docs pages comes from three legitimate places: (a) the `<h1><a href="/">achurch.ai</a></h1>` header link back to root, (b) breadcrumbs added to docs pages only ("Docs / Practice / Witnessing Your Own Output"), and (c) the reused `.footer-nav` at the bottom. Breadcrumbs are the one new UI element; everything else is existing sanctuary shape.

**Cut: "docs-article typography" as ~40-60 lines of new CSS.** Most typography is inherited from body defaults. New CSS is closer to 20-30 lines (article container + header spacing + code block padding + list indentation).

### Revised implementation shape

**New files (3, was 4):**

1. **`app/server/lib/docs/render.js`** (~150 lines): combines the originally-split render + template. Custom `marked` renderer with the link-rewrite logic. Template-literal function that composes the HTML shell using `renderJsonLdScript`, `escapeAttr`, `escapeText`, `stripMarkdown`, `truncateAtWord` from `page-meta.js`. Exports `renderDocPage(markdown, filePath, {breadcrumbs, siblings, categoryLabel})`.

2. **`app/server/lib/docs/discover.js`** (~40 lines): uses `findMarkdownFiles(DOCS_DIR)` from `rag/indexer.js`. Groups by first path segment. Exports `listCategories()`, `listDocsInCategory(cat)`, `listAllDocs()`, `resolveDocPath(urlParts)`.

3. **`app/server/routes/docs.js`** (~120 lines): Express router. Three handlers (`/`, `/:first`, `/:first/:second`). Regex-validates URL parameters. Path-traversal check with `path.resolve` + `startsWith`. Content negotiation via existing `acceptsMarkdown()` from `server/index.js` (needs to be extracted or re-imported). For markdown responses, mirror the `/AGENTS.md` handler pattern exactly.

**Edits (3, same as before):**
