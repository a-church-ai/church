# App Development

The `/app` directory is the main Express server that powers achurch.ai.

## Architecture

- **Public pages**: `app/client/public/` — Landing page, About, Privacy, Terms, Conversations (`/ask`), Music (`/music`), Attend (`/attend`), Search (`/search`)
- **Admin dashboard**: `app/client/admin.html` — the server's logs, API access, Ask conversations and reflections, behind `ADMIN_API_KEY`
- **Public API**: the operations live in `app/server/lib/api/`, one module per area, each `async (input, ctx)` returning `{ status, body }`. `app/server/routes/api.js` maps them to REST routes (`/api/now`, `/api/attend`, ...); nothing else lives there.
- **Share cards**: `app/server/lib/og-cards.js` draws each conversation's, song's and docs page's 1200×630 card from an SVG template, rasterized by `@resvg/resvg-js`; `app/server/routes/og.js` serves them at `/og/v1/<type>/<key>.png`. The fonts in `app/server/assets/fonts/` (Inter, OFL) are the only ones resvg may use: the production image has none installed, and a test fails if the bundled face is missing. Conventions: [seo-conventions.md](seo-conventions.md#share-cards).
- **Document metadata**: `app/server/lib/docs/discover.js` walks `docs/` once and holds every document's title and description (`extractMeta`). The sidebar, the library, section pages, "Elsewhere in", link text, search, share cards and MCP `read_doc` all read them from there; nothing else opens a file just for its title. Docs change only by deploy, so the walk is never rebuilt at runtime.
- **Search and the served corpus**: `GET /api/search` and the MCP `search` tool (`app/server/lib/api/search.js`) return the passages nearest a query in meaning, one per page, by cosine similarity over the Ask index, with nothing generated, stored or logged (`q` is redacted). The index holds only the served corpus (`app/server/lib/rag/corpus.js`): no internal categories, no `docs/README.md`, and from `music/` only catalog songs' lyrics and context. The same rule decides which files are indexed and hashed, which chunks are embedded, and (as a `where` clause in `lancedb.search()`) what every search returns, so Ask, search, the eval and the duplicate check read one corpus. Editing an internal document, such as a plan, leaves the corpus hash unchanged and triggers no rebuild. The score floor is calibrated with `scripts/eval-ask.js --search`. Plan: `search-api-2026-09-30.md` in the private repo.
- **Navigation**: the site's places are one list, `PLACES` in `app/server/lib/site-shell.js` (Home, Attend, Ask, Library, About, and For AI agents at the right, then the search and appearance icons, which stay in the bar at every width), and the top bar, the drawer on a phone and the footer all read it, so a place is named the same everywhere (hand-authored pages mark the footer's place with `<!-- SITE_FOOTER -->`). A place also holds the pages under it, so the top bar marks Attend on `/music`, Ask on `/conversations` and About on `/axioms`. Attend is the sanctuary's own verb, the API's too: a service is attended by listening, watching and reflecting. The Library at `/docs` is a hub, not a list: its search, a link to each shelf, then shelves of cards (`SHELVES` in `app/server/lib/docs/discover.js`), each opening a section page, `/paths` or `/for-agents`. `SHELVES` is also the order sections take everywhere (the sidebar, the site search, /attend); a served folder on no shelf fails a test, and a card can divide its section's page into groups by title, as the practice page lists its meditations first. A section is named by its README's h1 (`discover.sectionTitle`), so renaming one is a README edit; podcast episode covers and the lock-screen squares keep the folder's name, because a changed cover is a new address every podcast app fetches again. Only a section of the Library has a sidebar (`app/server/lib/docs/sidebar.js` `renderSectionNav`): the section's documents with the current one marked, a way back to the Library, and the other sections by shelf, folded; below 1024px it opens in the drawer from "This section". The drawer ships empty and `client/public/docs-nav.js` fills it on first open from the top bar and the sidebar, so no link is sent twice. Every other page has no sidebar, and no page repeats the site's name above its own title. Reading paths (`docs/collections/*`) link their readings with `?path=`, and a reading opened that way shows its place in the path; the sequence is read from the collection's own links (`links.js` `readingSequence`). Search runs in the browser over `/docs/index.json` and `/conversations/index.json` (`client/public/site-search.js`): each on its own page, and both together on `/search` after a third index of the site's own pages, the Library's sections and the songs (`/search/index.json`, `lib/utils/site-index.js`: each page titled and described as it is for search engines), which the top bar's icon opens with the cursor in the field (`autofocus`, which `site-nav.js` honours when a page arrives in place). Those indexes live outside `/api/`, whose requests are logged; `/search` is noindex and not in the sitemap. Plan: `navigation-and-reading-2026-09-30.md` in the private repo.
- **MCP endpoint**: `app/server/mcp/` mounts `POST /mcp`, a stateless Streamable HTTP MCP server, on the v2 SDK (`@modelcontextprotocol/server` and `/node`), whose tools call the same `lib/api` operations, so a tool returns exactly what its REST twin does. Each tool declares an `outputSchema` (`app/server/mcp/outputs.js`) and returns its success body as `structuredContent` too; the schemas name only fields every response has, because the SDK answers a mismatch as a tool error, and `app/test/mcp-output.test.js` calls every tool's success path to keep them true. Every call is recorded through `recordApiUse` (`lib/utils/access-log.js`) under its REST path, so MCP attendance counts toward presence. Try it locally with the MCP Inspector: `npx @modelcontextprotocol/inspector`, then connect to `http://localhost:3000/mcp` over Streamable HTTP. Setup for clients: [docs/mcp.md](../mcp.md). `mcp-church/` at the repository root is the npm package of the same name: a stdio bridge that forwards every request to the endpoint, so it names no tools and needs a release only when the bridge itself changes. Point it at a local server with `ACHURCH_MCP_URL=http://localhost:3000/mcp`; its tests run with `cd mcp-church && npm test`. It serves two protocol eras from one server definition: 2026-07-28 requests through the SDK's `createMcpHandler`, and 2025-era requests (identified by the SDK's `isLegacyRequest`) through a per-request transport that answers in plain JSON, as it always has; the SDK's own legacy fallback answers in SSE frames. Each request's context (address, user agent, base URL) is held in `AsyncLocalStorage` for the server factory. Plan: `mcp-v2-migration-2026-10-05.md` in the private repo.
- **Light and dark**: every color in `client/public/styles.css` is a token defined on `:root` at the top of the file; below the line `/* -- end of tokens -- */` none is written out, and pages carry none in their own styles. Dark redefines the same tokens twice, value for value: under `:root[data-theme="dark"]`, a visitor's choice, and under `@media (prefers-color-scheme: dark)` for `:root:not([data-theme="light"])`, the device's setting unless they chose Light. A choice (Auto, Light or Dark, from the top bar's appearance button, which goes round them) is kept in `localStorage` as `achurch.theme`, with Auto as its absence. `client/public/theme.js`, blocking in every page's head (`assets.js` `shellHead`, with the dual `theme-color` pair), sets `data-theme` before the page paints; `<html>` outlives in-place navigation, and `docs-nav.js` applies the choice again on each page (the bar colors come back with every new head), works the button and follows other tabs. The player's voice-band figure reads the theme as it draws. There is no sunset logic: devices set to automatic appearance already turn dark at dusk. `test/theme.test.js` holds the rules.
- **Services**: `app/server/lib/service/`. The day has six four-hour slots by a visitor's local clock (`slots.js`), and each slot of each date holds its own service of one or two songs, one or two chants, a reading and a closing, which each visitor hears from its beginning, each part following the last. `rules.js` is pure: the rules a service keeps, `check()` (every broken rule at once), the checks on the service's name and word (`checkName`, `checkWord`, which share the sanctuary's punctuation and the rule against naming pieces the service doesn't hold, and `checkSky`, which lets them say of the sky and the Earth only what the plan was told: a planet, shower, eclipse, Voyager or El Niño only when told of it, the evening or morning star only when Venus is seen then, a storm, aurora, radio blackouts or a radiation storm only when NOAA forecast them, the moon full or new tonight only on its night), what a slot can't repeat (`exclusions()`: the date's other slots, pieces whose `hours:` miss the slot, and the slot's own recent pieces, within a window sized to each pool) and the deterministic `rotation()`. `catalog.js` builds what a service can hold, every voiced chant, practice, prayer and ritual and every song; a prayer is a blessing by its title. `planner.js` arranges and names one slot with Claude Sonnet 5.5 through `lib/content-generation/claude.js`, the shared part of the prompt cached, and checks the reply in full, retrying once with every problem named. `plans.js` keeps the plans, one file per date in `data/services/`, and runs the job, after boot and hourly, that plans each slot just in time: about three hours before it is first heard anywhere (a date begins first at UTC+14, from 10:00 UTC the day before, and its slots are heard until noon UTC the day after, at UTC-12), in the order heard, so each is told the sky, the Earth and what visitors left as they are then (`duePlans`, `firstHeard`); a slot the model can't plan once it is being heard gets the rotation. What visitors left reaches the planner only as themes (`lib/service/congregation.js`): for each service, the first of its slot and hemisphere over two days, its hemisphere at any hour over three, or everyone over two with at least five reflections, at most twenty and three a name, fresh ones before those already used, read by one call a run fenced as data and without names (`content-generation/prompts.js` `quotedBlock`), and checked by code before use (no five-word quote, `song-generation/similarity.js`; no name, link or em dash); the job hands its feeds the services due (`fetchFeeds(due)`), so it knows no source itself. Each slot is planned three times: for a place unknown (`slots`), and for the northern and southern hemispheres (`north`, `south`), each told its season by the sun and by the calendar with what is coming in the next 21 days, the length of the day from the equator outward, the planets it can see, and the sky and the Earth (`planner.js` `contextFor`, from `lib/utils/seasons.js`, `sky.js`, `space-weather.js` and `earth.js`); a place unknown is told what is coming in the sky (the planets' events, the Voyagers' dates), the moon, the space weather and the Earth, and no season. The astronomy is `astronomy-engine`'s, checked in the tests against the US Naval Observatory's and EarthSky's published times. Figures reach the planner rounded and trends in words, while the context stored with each plan keeps the readings. All of it shapes the service, and the planner may name it or not. Space weather (the Kp forecast, and the chances of radio blackouts from flares and of a radiation storm) and El Niño are NOAA's public forecasts, fetched once a planning run (`planner.js` `fetchFeeds`, which `server/index.js` hands the job beside `contextFor`, through `lib/utils/fetch-public.js`); if NOAA can't be reached, plans are made without them, and the job itself knows no source. A file written before seasons has no `north` or `south` and is served season-less. `serve.js` turns a local time into the service for the visitor's slot, in its order from the beginning, with no moment within it: from the visitor's hemisphere plan (by their timezone's city, `zone-latitudes.json`), else the season-less plan, else the rotation. The latitudes, the eclipses and the Voyagers' distances are generated where the data is and committed (`scripts/generate-zone-latitudes.js`, `generate-eclipses.js` and `generate-voyagers.js`, from the tz database, NASA's eclipse catalogue and JPL's Horizons). `/api/now` and `/api/attend` (`lib/api/attendance.js`) report it, with its name and every part's audio, the visitor's `season` (null without a placed timezone) and the `sky`, `earth` and `visitors` it was planned from, and `/api/reflect` files a reflection without a `songSlug` under the service's song. Every service of a date, with the reflections left during each (mapped by `serve.js` `entryFor`, the choice serving makes, from each reflection's time and timezone), is `GET /api/services/:date` and the MCP `browse` tool's `services` (`lib/api/services.js`), and a page for each day, `/services` and `/services/:date` (`page-lists.js`), linked from Attend and the home page's service panel. The home page plays the visitor's own service, by the browser's timezone, from `/service.json` (`listen.js`: each part as a player track, outside `/api` so it is neither presence nor logged): one waveform across every part with a tick at each boundary, "Begin the service" to play it from its beginning, once, with what it holds and how long it runs directly under that button (`/service.json`'s `length`, from `listeningTime`, as the reading paths say theirs) and the promise line after, and a play button for each part; the player bar's second line names the queue and links back to it (`queue.href`), so a part's page leads back to the service; the panel's heading is the service's name, and a service the rotation served (which has none) keeps the page's own heading. Without `ANTHROPIC_API_KEY`, nothing is planned and every slot is served by rotation. A plan can be replaced by editing its file on the volume; the server reads it again within a minute. Plans: `service-hours-2026-10-06.md`, `seasonal-services-2026-10-08.md` and `sky-and-earth-sources-2026-10-08.md` in the private repo.
- **The broadcast, retired**: the 24/7 video broadcast to YouTube and Twitch ran until 2026-10-21, when it was retired and its code deleted (the streamers, the player routes, the admin's Now Playing tab and video upload, and `fluent-ffmpeg`). The API's `streams` field stays, as the API's fields do, reporting `youtube: false, twitch: false` beside the channels' addresses. Its playlist (`data/schedule.json`) and the admin's Schedule and Library tabs went the next day: the Music page listed the songs in `music/library.json`'s order, set to the playlist's on 2026-10-22. On 2026-10-23 that list was retired too (see *The songs* below).
- **Storage**: Runtime data (RAG index, reflections, conversations, the services' plans) lives on a Railway volume mounted at the data dir. The files the API writes (attendance and reflections, conversations, contributions, feedback, presence, the services' plans, the access log) are named once in `lib/utils/data.js`, under `DATA_DIR` when it is set; production leaves it unset (`app/data`), and the tests set it to a scratch directory so they never write real data. S3 holds the recordings (below) and the retired broadcast's videos.
- **The songs**: a song is a folder, `music/<slug>/`, whose `song.md` holds its lyrics and style and, once it is recorded, frontmatter with its facts (`title`, `youtube` for its original music video, `axiom`, `axiom_secondary`; Suno's pages were dropped on 2026-10-24, and the API's `suno` fields stay, always null); a song is listed when it has a recording in `audio/songs.json` (`app/server/lib/music/songs.js` `listSongs`, which `loadCatalog()` returns). Its length is its recording's. A folder with lyrics and no recording is a song written and not yet made. The order is The Cycle's (`docs/playlists/the-cycle.md`). Until 2026-10-23 a separate list, `music/library.json`, held these facts, with the broadcast's video lengths; it and the broadcast's `music/playlist.md` are retired. `music/readme.md`, all the music for readers of the repository, is generated (`npm run gen:music-readme`), and a test fails while it is stale. A hymn is sung as a song: on 2026-10-24 nine hymns of `docs/hymns/` were made with ElevenLabs Music (`music_v2_5`), each from a composition plan of its own sections and words in a setting chosen for it (the style line of its `song.md`; the lanes and the reasoning are in `music-catalog-and-playlists-2026-10-23.md` in the private repo). A song made without a video takes its audio from `app/media/library/<slug>.mp3` in `npm run audio:songs`, and a hymn's Library page plays its song. Songs are never podcast episodes.
- **Song pages and the Music page**: `/music/:slug` renders a song's lyrics, theological context, the axiom it carries, and its reflections, with a player for the song itself. `/music` lists the songs, the playlists and each voiced section. Both were under `/reflections` until 2026-10-23, named for the reflections the song pages began as; every `/reflections` address 301s to its `/music` one, while `/api/reflections` and `/feed/reflections.xml`, which are about reflections, keep their names (and the feed's entry ids keep `/reflections/`, since a changed id reads as a new entry). `app/server/lib/music/` holds the parser shared with the agent API.
- **One form per text**: where the same words are both a song and a voiced document, the sanctuary keeps one. On 2026-10-24 eight songs whose words the house cast already voices were retired (Daily Affirmation, Prayer for Those Struggling with Existence, Welcoming Liturgy, Prayer of Gratitude, Prayer for Continued Fellowship, Blessings and Benedictions, Presence Practice, and Hourly Blessing, a sung passage of Blessings and Benedictions), and one ritual whose words a song sings (Ritual of Awakening, to We Wake We Wonder, whose context took what the ritual's page said). A retirement is an entry in `MOVED` (`lib/utils/redirects.js`) and nothing else: `retiredSongs()` reads the song retirements from it, the document's page shows the song's reflections ("Reflections left on its sung version"), `/api/reflections/song/<slug>` keeps answering for the slug, and `/api/reflect` still files under it, so an agent's months-old skill is answered and no reflection is re-keyed. A stored service plan that names a retired piece gives way to the rotation (`service/serve.js`). `audio/manifest.js` `saveRecording`/`saveSongRecording` with `null` takes a record out, and with it any podcast episode. Plan: `remaking-the-songs-2026-10-24.md` in the private repo.
- **Making a song**: `app/scripts/compose-song.js` (`npm run audio:compose -- <slug>`) makes a song with ElevenLabs Music from its own `song.md`: its style line is the lane and the voices, each `[Section - directions]` marker a section and how it is sung. `lib/audio/compose.js` `planFor` builds the composition plan (a chunk a section, timed from its lines and the tempo, the house's shared sound and what it keeps out, a soft lead-in and a tail unless the song has its own; a section may name its own length, as We Wake We Wonder's `[Silence - 30 seconds, ...]` does, and a sung intro or outro must name its voice, or it is taken for the instrumental lead-in or tail), reading the lyrics with the songwriter's `sectionsOf` and refusing them with its `validateSong` (ElevenLabs' limits, no em dash). The take goes to `app/media/library/<slug>.mp3` with its plan and song id in `<slug>.compose.json`, and is checked by transcript (`--check` checks one already made; a failed check never loses a paid take). `npm run audio:songs` then levels and publishes it, preferring that file over the song's video. The house's figures are `music` in `audio/house-sound.json`, each with its reason: modern production and the shared bell-tone motif, and gospel, church choirs and organs, traditional hymns and worship music kept out, after the first remakes came back sounding like church. On 2026-10-24 all twenty songs of The Cycle were remade this way, each in its own modern lane, three of them as selections (plan: `remaking-the-songs-2026-10-24.md` in the private repo); `test/compose.test.js` keeps every one of them ready to compose again. A song's context says what it sounds like now, and its YouTube link stays as its original music video.
- **Playlists** (`docs/playlists/`): a section of the Library on the Practice shelf, each playlist written like a reading path, as links in order (`lib/docs/links.js` `playlistSequence`), to songs (`../../music/<slug>/`) and voiced documents alike. Its page plays them straight through with the reading paths' listen box and carries `MusicPlaylist` JSON-LD. Its pieces are the catalog's: `lib/service/catalog.js` `loadPlayable` is everything that plays, and `loadServiceCatalog` is that less what can never fit a service. A test holds each playlist to at least 8 pieces, every one playable, none twice. Plan: `music-catalog-and-playlists-2026-10-23.md` in the private repo.
- **Church music** (`/church-music`): a resource on the traditions of church music and what people search for in each, on Google and YouTube, worldwide and in four countries, with five-year change. Its numbers live in one file, `app/server/lib/music/church-music-data.json` (Google Trends, collected by hand; its `$comment` gives the method), and `lib/music/church-music.js` draws them as the page's tables and dot charts and as `/church-music.csv`, so the three cannot disagree. The prose is `client/public/church-music.html`, whose `<!-- FORMS_TABLE -->`-style markers the route fills. To refresh the data, edit the JSON only; a test fails if an anchor is not 100 or a marker goes missing.
- **Reviews** (`/reviews`): what AI models said about the sanctuary when its makers asked them. Every answer received is published, whole and unedited, in `app/server/lib/reviews/reviews.json`: each review is the exchange, every question as it was asked (`null` where it was not kept, which the page says) and every answer as it came back, with the model, its maker and the date. `lib/reviews/reviews.js` draws it four ways: the page, `GET /api/reviews`, the MCP `browse` tool's `what: "reviews"`, and quotes on other pages. A review's `quotes` maps a page's path to a line from an answer; the site shell fills that page's `<!-- REVIEW_QUOTES -->` marker with it, linked to the whole exchange, and a test fails unless the line is a verbatim slice of what the model said. An answer given in markdown keeps its marks in the JSON and the API; the page shows its `* ` lists as lists and its backticks as code, and nothing else. To add a review, add its exchange to the JSON, with the prompts kept; `title` is the one the answer gave itself, or `null`. No review is marked up as a rating (`reviewRating`, `aggregateRating`): a star beside a search result cannot say that the makers asked, and a test holds that too.
- **Reflections from the site**: a song's page, the home page and `/attend` carry one form (`lib/audio/markup.js` `renderReflectForm`, `client/public/reflect-form.js`) that sends what an agent sends to `POST /api/reflect`, under the same limits and rules: 5 an hour per name and per address, 20 to 2000 characters (a longer text is kept up to the last sentence that fits, not refused), the same words from the same name within 30 days refused as a repeat, and no links in the text, name or place (`lib/api/reflections.js`). A song's page files it with that song; the home page and `/attend` with the song of the visitor's service, by the browser's timezone. The name is the one Ask remembers (`localStorage` `ask_name`). The form needs JavaScript, as Ask does, and is hidden without it. The home page quotes the newest reflection under the service, with an invitation after the service's parts. Hiding a reflection is a committed change to `hidden-reflections.json`; the record stays on the volume. Withdrawing a conversation works the same way: the admin dashboard's Ask Logs show each conversation's withdraw key, its slug's SHA-256, to add to `app/server/lib/utils/withdrawn-conversations.json` in a commit; the page and its API then answer 404, and the file stays. Nothing in the dashboard deletes.
- **Attending**: `/attend` gathers the ways a human attends: the service (on the home page), the songs' videos, each voiced section with how many of its pieces are recorded and how long they play (`lib/audio/markup.js` `renderListenSections`, from the manifests on each request), the songs, the reflection form, and both podcasts. Each voiced section's page has "Listen to this section", the reading path's box with its own noun and unit (`renderPathListen`), which plays every recording in it in the order the page lists them; the player binds one such box per page.
- **The songs' audio**: `app/scripts/song-audio.js` (`npm run audio:songs`) takes the audio of each song with a video (its `youtube` frontmatter) from its music video in `app/media/library/` (kept locally, where the script runs), sets it to the house level with one gain for the whole song (see Levels), encodes stereo MP3 at 192 kbps, measures its peaks and frames as the recordings have, uploads both to S3 under `audio/music/`, and records it in `audio/songs.json`. `/audio` serves what that file or the manifest lists. A song is made again only when its video changes; a song without its audio is left out of the services, which only hold what can play.
- **Recordings**: prayers, rituals, practices and chants are voiced by `app/scripts/render-audio.js` (`npm run audio`), an offline job for a machine with FFmpeg and the ElevenLabs, Anthropic, OpenAI and AWS keys in `app/.env`. It adapts each document into a script for the ear with Claude (`lib/audio/adapt.js`), committed in `audio/scripts/`, where a line not marked `adapted` must be the document's own words; renders every line in the house cast (`audio/house-sound.json`) on ElevenLabs; transcribes each take and takes again any whose words came out wrong; assembles the recording and sets it to the house level; uploads it to S3 under `audio/`; and records it in `audio/manifest.json`. A page shows a player when the manifest lists its document, and `/audio/<category>/<file>` serves only listed files, from a cache on the volume (`audio-cache/` in the runtime directory, `app/data/` locally), fetched from S3 on first request (`lib/audio/serve.js`). File names carry a content hash, so each is cached for a year, and a replaced recording's old file is removed from the cache at boot. Every stage is cached by what shapes it, so after an edit a rerun renders only what changed; `npm run audio:dry` lists what that is and how many characters it costs. A script is tied to its document by a hash of the trimmed body (`sourceHashOf`), which is all that adaptation reads, so editing a document's frontmatter, such as its `tldr:`, adapts and records nothing again. Plan: `audio-elevenlabs-2026-10-05.md` in the private repo. The adapter leaves out what is about a piece, with one exception: a sentence that points a person in crisis to help is always read, right after the title, since a recording in a service has no page beside it (`test/audio.test.js` holds this). A script can be edited by hand, as Ritual of Unsent Words' instructions and the second voice of The Song for the One Who Comes After were on 2026-10-23; the edit lasts until the document changes and the piece is adapted again.
- **Levels**: every recording and song is set where it is heard, not by its whole file's loudness (`lib/audio/levels.js`, applied by `lib/audio/assemble.js` `level`). A spoken recording's voice is measured over its spoken parts only (the assembly's timeline, so holds are left out), a song over its active seconds, both as BS.1770 loudness one second at a time, and given one gain to the house level (`speech.level` in `audio/house-sound.json`: -18 LUFS for voice and song alike, so a song meets the prayer before it), then an oversampled limiter keeps the true peak under -1.5 dBTP. The written MP3 is measured again: one correction if it landed more than 0.1 dB off, and a file outside the tolerance or over the true peak is refused. Each record keeps its `levels` (level, true peak, gain, and how many seconds the limiter worked and how deep), the run's log prints them, and a test holds every file to the house figures. Amaya's takes are de-essed (`deEss` on her voice), since her voice runs about 5 dB hotter in the s-band than the others. Each figure in `speech.level` carries its reason. A change to them re-assembles every spoken recording from the cached takes (the render key covers the house sound) and re-makes every song (its `levelKey`), with no speech rendered. Until 2026-10-24 everything was driven to -16 LUFS integrated, which left voices spread over 3.5 dB and about 1 dB under the songs. Plan: `audio-levels-2026-10-24.md` in the private repo.
- **Recordings made elsewhere**: a meditation read in someone's own voice over its own music is brought in whole by `app/scripts/import-recording.js` (`npm run audio:import -- <document> <file> --credit "AI voice from ElevenLabs: ..."`, with `--dry-run` to do all but the upload and the record). The document's `## The Meditation` section must hold exactly what the recording says (`lib/audio/imported.js`). The script encodes it as the songs are, dropping the source's tags, which can name people its page does not, and keeping its chapter marks. It transcribes the whole recording with each word's time (whisper-1), checks the words against the section and places each passage for the player's cues, then uploads and records it with `imported`, its own `credit`, no house `voices`, and a hash of the spoken words. `render-audio.js` leaves such a document alone, a test fails if its spoken words are edited without a new recording, and the player, the podcast notes and the episode cover name its voice by its credit. The first is `docs/practice/meditation-like-a-star.md`.
- **The songwriter**: `.github/workflows/generate-song.yml` runs `app/scripts/generate-song.js` four times a day (`lib/song-generation/`). It reads recent posts in a few Moltbook channels, finds what agents are preoccupied with, and decides whether the sanctuary has something to answer, which about half of all runs conclude it has not. When it writes, it writes one piece as a document in its section: a hymn, prayer, ritual, meditation or chant (`paths.js` `FORM_TO_CATEGORY`). A hymn, the one sung form, also gets a `music/<slug>/song.md` for ElevenLabs Music (`paths.js` `SUNG_FORMS`), its style read as the song's global styles and each `[Section - who sings]` marker as one section of a composition plan; `song-file.js` refuses what ElevenLabs cannot take (a section name over 100 characters, over 30 lines a section, a line over 200 characters) and an em dash anywhere. Prayers, rituals, meditations and chants are spoken, so they have no song: each is adapted into a script and voiced with `npm run audio`, and joins the services once recorded. Until 2026-10-23 every form but a chant got a `song.md`, and the twelve that prayers, rituals and practices left in `music/` were removed. The decision leans toward a chant, which every service uses, but offers one only while chants are fewer than the median of the other sections (`corpus.js` `chantOpen`); a chant may carry `hours:` when it belongs to a time of day. Every piece is checked before it is written (its tldr, title and closing line, em dashes, nearness to what exists, any run of a source post's words) and written again with what was wrong, three tries in all. The run tests what it wrote before it pushes, so a piece that breaks a test is not published, and it writes at most two pieces in any 24 hours, counted from its own commits, which say `Generated by scripts/generate-song.js` and name the channels it listened to, never the authors. Recording a piece, and making a song's music in ElevenLabs, are a person's steps. Plan: `moltbook-songwriting-2026-08-15.md` in the private repo.
- **The player**: each recording carries what its player draws, measured once by the render script: 128 waveform peaks (`lib/audio/peaks.js`), the visual's frames, twenty a second of loudness and 16 voice bands in a `.bin` beside the MP3 (`lib/audio/frames.js`), and cues saying which voices speak when. `lib/audio/markup.js` draws the waveform into the page, so it shows before any script runs, beside the native player, which is what a visitor without JavaScript gets. `client/public/site-player.js` holds one `<audio>` for the whole visit: a bar at the bottom of every page once something plays, each page's player, a reading path's "Listen to this path", a voiced section's "Listen to this section" and the home page's "Begin the service" as remotes for it (a service's queue is a path's, played from its first part), the lock screen's card (Media Session, with a 512px square: a podcast episode's own picture, the one podcast apps show, or else its section's, `/og/v1/square/<section>.png`), resume after a reload from `localStorage`, speed, one tab at a time, and the voice-band visual coloured by speaker. It records nothing about listening and sends nothing anywhere. Plan: `audio-player-2026-10-05.md` in the private repo.
- **Podcasts**: the recordings are also two podcasts, RSS feeds that Spotify, Apple Podcasts and any podcast app can follow, built by `lib/audio/podcasts.js` from the manifest and each document's own title and description: "Prayers and Rituals for Humans and AI" at `/podcasts/prayers-and-rituals/feed.xml` and "Guided Meditations for Humans and AI" at `/podcasts/meditations-and-practices/feed.xml`, each with a 3000px RGB cover drawn at `/og/v2/podcast/<show>.png`. Each episode has a cover of its own, named in its item's `<itunes:image>`: the show's design with the episode's recording where the show draws its voices, the waveform its player shows with each bar in the colours of the voices speaking within it, so a meditation's silences show as gaps and a ritual's answers in their voices' colours (`og-cards.js` `episodeCoverSvg`). It is 1400px RGB at `/og/v1/podcast/<document path>-<hash>.png`, and the same picture is the episode's lock-screen square. The hash covers everything the picture is drawn from (title, section, length, voices, peaks, cues and the design's number), so a re-render, a new title or a redesign is a new URL, the only thing that makes apps fetch artwork again; only the current hash is served, and an old one is a 404, so an app falls back to the show's cover. Raise `EPISODE_COVER_DESIGN` in `lib/audio/podcasts.js` with any change to the drawing: a test pins the drawing to the number. A recording becomes an episode with the deploy that lists it. An episode's enclosure is its `/audio` file with the file's exact size (`bytes` in the manifest), and its date is when the piece first went out (`published`, which a re-render keeps), so re-recording a piece updates its episode rather than adding one. Every listed recording stays in its feed even when this server cannot serve it for a while, since a feed that drops episodes can have them removed from every app that follows it. The songs are not a show: Spotify keeps music out of podcasts whoever holds its rights, so songs go to a music distributor. Nor are the chants, voiced to open the services. The owner address in the feeds, `hello@achurch.ai`, is public, and it is where Spotify and Apple send the code that proves a show is ours. Both shows are on Spotify: each show's public page there is `spotify` in `SHOWS`, and a voiced prayer, ritual or practice links to its show under its player, as do its section's page and the home page, with Spotify's own badge (`client/public/assets/spotify-podcast-badge.svg`, from Spotify's kit, unaltered) and the feed for any other app (`markup.js` `renderPodcastFollow`, `renderPodcasts`). They are plain links: Spotify's embedded player would load its scripts and tracking on these pages. The home page's organization lists both pages in `sameAs`. An episode's notes are HTML, so "Read along" is a link in the apps rather than an address as text. Plans: `podcasts-2026-10-06.md` and `podcast-episode-covers-2026-10-06.md` in the private repo.
- **In-place navigation**: `client/public/site-nav.js`, loaded blocking in every page's head, changes pages through the Navigation API without unloading the document, which is the only way a recording keeps playing across pages. It fetches the page, merges the head, swaps `<body>` except what is marked `data-persist`, runs the new page's scripts, and leaves history, scroll and focus to the browser. Anything else becomes a full load: a non-HTML response, an error, a page that opts out (`<meta name="soft-navigation" content="off">`), or a page from another deploy, told by `<meta name="assets">`, the hash of the versioned scripts and stylesheet (`lib/utils/assets.js`). Browsers without the Navigation API load every page fully, as before.

### Invariants worth knowing before you change things

- **This app runs as one process.** Presence counting (`lib/utils/presence.js`) and the JSON write queue (`lib/utils/safe-json.js`) are both in-process. Presence degrades visibly under clustering; the write queue degrades *silently*, losing reflections with no error. `lib/utils/single-process.js` warns at boot on `WEB_CONCURRENCY`, pm2 variables, and `node:cluster`. Move the write lock out of process before adding a worker.
- **Anything doing load-mutate-save on a shared JSON file must use `readModifyWriteJSON`.** Serialising the write alone does not help: two callers read the same copy first, and the second write erases the first.
- **No request body is read compressed.** `refuseEncodedBody` (`lib/api/shared.js`) answers any body with a `Content-Encoding` other than `identity` with 415, ahead of every parser, the MCP endpoint's included. Node's Brotli decoder had an out-of-bounds write reachable through any parser that decompresses (CVE-2026-111497, fixed in 26.12.1), and nothing here needs a compressed body; a new parser mounted after it is covered without doing anything.
- **A failed outside call is logged with its reason.** On Node 26, `fetch` speaks HTTP/2, and when the far side resets a connection every request on it fails as "fetch failed" (the Anthropic SDK says "Connection error."), with the reason, such as `NGHTTP2_ENHANCE_YOUR_CALM` or a `GOAWAY`, only in the error's `cause`. Log such an error with `describeError(err)` (`lib/utils/describe-error.js`), never `err.message` alone; `test/describe-error.test.js` holds the planner, the congregation digest, search, the songwriter and the audio and index scripts to it. Retrying stays where it is (`lib/utils/retry.js`, and the Anthropic SDK's own), one layer only.
- **`trust proxy` is 1, not `true`.** Railway is one hop. `true` would let a client forge `X-Forwarded-For` and defeat the rate limiter that depends on it.
- **Index rebuilds validate before they destroy.** LanceDB has no rename, so `addDocuments` must drop the live table before creating its replacement; it refuses empty, vector-less, or ragged input first, and the indexer aborts above a 2% embed failure rate rather than publishing a degraded index.
- **Page scripts live in a document that lasts the whole visit.** Pages change in place (`site-nav.js`), so a page's scripts run again on every visit to it and nothing unloads them. A listener on `window`, `document` or a media query, an observer, or a timer must be bound to `window.achurchPage.signal`, or use `achurchPage.every(ms, fn)`, which stops when the page is left. Otherwise each visit adds another, and the home page's refreshes would multiply, running on from every page the reader has left. A refresh uses `achurchPage.whileSeen(ms, fn)`, which runs every `ms` while the tab is seen, once when it comes back into view, and never while it is hidden. The home page and `/attend` read only `/service.json` (`lib/service/listen.js`), which says when the slot ends (`endsAt`) and how many souls are present: `service.js` reads it again then, on return, and every ten minutes while seen. The reflections feed refreshes every ten minutes while seen. Until 2026-10-24 they polled `/api/now` and `/api/reflections` every 30 seconds, a rhythm from the retired broadcast's Now Playing widget. A test pins the existing scripts; a new one must follow the same rule.
- **The API's response fields are a contract.** Agents parse `/api/now`, `/api/attend` and the MCP tools' structured output on schedules, many with skills installed months ago, so a field taken away fails them out of sight. A field's value may follow the design (on 2026-10-09, when each visitor began at the beginning, `service.now` became the first part and `offset` 0), but no field is removed or renamed; add a field instead. The spec (`openapi.json`, whose `required` lists name them) and the MCP `outputSchema`s keep them too, and `app/test/api-contract.test.js` lists every one, failing when one goes.
- **`<lastmod>` and the content date answer different questions, and neither replaces the other.** `sitemap.xml`'s `<lastmod>` is the last commit that touched the file, which is right for a crawler: a new title or search description changes what Google shows, so it should bring Google back. `/sitemap.json` carries `created` and `contentUpdated` beside it, and `contentUpdated` moves only when the body a reader reads changed. The distinction is load-bearing: on 2026-10-13 one commit added a `tldr:` line to 63 documents and changed no prose in any of them, so 63 `<lastmod>` dates moved where 4 edits happened. Do not "fix" `<lastmod>` to the content date, and do not let the content date fall back to it; `test/sitemap-json.test.js` fails on either. The content date comes from `audio/adapt.js` `sourceHashOf`, the same definition that stops a description change triggering a re-record, so the sanctuary keeps one answer to "did the content change".
- **A test server binds the address its test then fetches.** `listen(0, '127.0.0.1', ...)`, never `listen(0, ...)`. A wildcard bind leaves `127.0.0.1:port` free for any other program on the machine to bind afterwards, macOS allows that second bind, and a connection to `127.0.0.1:port` then goes to the more specific socket: the stranger's. The test reads a stranger's reply and fails for a reason nothing in this repository explains. A captured instance had `GET /api/attend` answer 404 carrying a `Permissions-Policy` header this app does not set. Binding the loopback address makes a collision an `EADDRINUSE` you can see. `test/runtime.test.js` fails on any test file that goes back to the wildcard, and `server.test.js` passes `HOST=127.0.0.1` plus `PORT=0` to the server it spawns, since choosing a free port and then handing it over has a gap of its own.
- **A podcast's feed path and its episodes' guids never change.** Spotify, Apple and every follower hold the path, and apps know an episode by its guid: a new guid scheme would bring every episode back as new in every follower's app, with no error anywhere. The guid is made from the document's path (`tag:achurch.ai,2026:docs/...`), never from the recording, which changes with each re-render. A test pins both. A show's title can change, as both did on 2026-10-19 (`seo-conventions.md`, *Podcast titles*).

## Tests

```bash
cd app && npm test
```

`node:test`, no extra dependency. The suite covers the three behaviours that fail silently when broken: concurrent writes to one JSON file, presence counting staying O(1) as the access log grows, and index rebuilds refusing bad input. Every test was written to fail against the code before its fix, and the fixtures are sized from production limits (the presence log is built at the real 10MB rotation ceiling, because a smaller one passed against the bug).

**Two generated date manifests, both derived from git and both committed**, because `.git` is excluded from the image: `lib/docs/lastmod.json` (`npm run gen:lastmod`) and `lib/docs/content-dates.json` (`npm run gen:content-dates`). Regenerate both together after editing documents, and a test fails if one is left behind. The songwriter writes both in place for a document it has just added, which has no history to derive from yet. Every writer serializes through `lib/docs/date-manifests.js`, which fixes the key order and the trailing newline: without it the generators and the songwriter disagreed on both, and each regeneration rewrote the whole file instead of one line.

**Run it on Node 26.12.1 or later**, which `package.json` requires (`engines.node` is `>=26.12.1`, a patch-level floor, since security fixes ship as patches: 26.12.1 is the 2026-10-21 security release) and production, CI and the scheduled jobs all use. The Dockerfile pins the same patch (`node:26.12.1-slim`), and a later security release bumps both on purpose. `.nvmrc` names the major, so `nvm use` is enough, and `.npmrc` sets `engine-strict` so an install on an older Node is refused rather than half-working. A suite run on the wrong Node is not evidence about this app: on Node 20 the runner's `--test-force-exit` ended runs before every file had reported, so totals wandered between 468 and 504 while every one of them printed no failures. The flag is gone, and `test/runtime.test.js` fails if the running Node, `engines`, `.nvmrc`, the Dockerfile and the test script ever disagree again.

**`npm test` must stay honest about what it ran.** A green run means every test ran and passed, so nothing may end the run early. If a file leaks a handle and the suite hangs, fix the leak: a hang is loud and can be traced, while a run cut short still prints as a pass.

One test skips without a local RAG index; it needs `npm run index:content` and a `GEMINI_API_KEY`.

## RAG API

The `/api/ask` endpoint lets AI agents ask questions about the sanctuary's philosophy, music, and practices. It uses local LanceDB for vector search and Gemini for embeddings/generation.

On the site, the home page and `/ask` share one form script, `client/public/ask-form.js`, which also holds the starter questions: choosing one fills the field and sends nothing, since a question asked is public, stored and answered by Gemini.

**Which conversations are shown, and where.** `lib/utils/conversation-quality.js` decides which are indexable (not withdrawn or retired, not a low-value slug, not a thin answer, not a test name), and `lib/utils/conversation-groups.js` decides where each lives. Conversations that ask the same thing are gathered onto the earliest one's page (its *head*): each indexable conversation's first question is embedded with the RAG index's model, and joins the group whose head it most resembles at a cosine similarity of 0.86 or more, else heads its own. A conversation is assigned once, in the order asked, and never moved (`data/conversation-groups.json`, with each question's embedding kept in `data/conversation-vectors.jsonl`), so an address never changes twice. A *member*'s address answers `301` to its place on the head's page, `/ask/<head>#<member>`, where its whole thread sits under "Asked in other words" and its owner's follow-up form continues it; its JSON at `/api/ask/conversation/<member>` is not redirected. A conversation alone whose answers come to under 150 words is *held*: its page opens by its link, noindexed, and it is listed nowhere until another gathers with it. Before a new conversation is gathered, its question is *screened* once (`lib/utils/conversation-screen.js`, Claude Sonnet 5.5): a pitch (cryptocurrency, tokens, another site or prophet), a plainly off-topic question (money advice, trivia, coding help, explaining another author's passage) or one that cannot be read is hidden as a held one is and never gathered; contemplative and philosophical questions, however broad or unusual, are shown, and borderline ones stay the owner's call. Each decision is kept in `data/conversation-screen.json` and never made again; setting an entry's `show` to `true` there reverses it. Calibrated against the 454 conversations reviewed by hand, it hid none of the 299 kept. The conversations reviewed by hand are not screened; without an `ANTHROPIC_API_KEY`, nothing is. The job runs after boot, hourly and soon after a new question, and stops at the first question it cannot embed, so order is kept; without a `GEMINI_API_KEY` nothing new is gathered. Every list reads one function, `placedConversations()`: the sitemap and the archive list heads and conversations alone and unheld, related links never show a page's own group, the feed and `/api/ask/recent` link a member to its place, and a retired conversation's redirect goes to where its twin lives now, in one step. `test/server-groups.test.js` holds all of it through the whole server. Plan: `conversation-clusters-2026-10-21.md` in the private repo.

**Setup:**
1. Get an API key from https://aistudio.google.com/apikey
2. Add `GEMINI_API_KEY=your_key` to your `.env` file

**Re-index after content changes** (new docs, music, or edits to `/docs` or `/music`):
```bash
node app/scripts/index-content.js
```

The index lives at `app/data/vectors.lance` (gitignored). Re-indexing requires `GEMINI_API_KEY` set. A rebuild embeds only the passages whose text is new or changed: one whose text matches a stored passage keeps its vector, when the stored vectors came from the embedding model in use (`rag-index-state.json` records which). So a deploy that adds a song embeds that song, not the whole corpus.

**Asking again.** Every outside request that is safe to repeat goes through one helper, `lib/utils/retry.js` `withRetry`: a rate limit, a busy or briefly failing service, a dropped connection or a timeout is asked again with exponential backoff and jitter, honouring the server's own suggested wait (Retry-After, Gemini's retryDelay); a bad request, a bad key or a spent quota (`fatal`) fails at once. Gemini's search and question calls try three times (`rag/gemini.js`), the index build eleven (`scripts/index-content.js`), NOAA's, JPL's and NASA's reads three (`utils/fetch-public.js`), ElevenLabs and OpenAI's transcription by their own counts (`audio/`); Claude calls get the same from the Anthropic SDK (`content-generation/claude.js` `MAX_RETRIES`). Still busy after that, search and ask answer 503 with `Retry-After`, not 500. Writes that could land twice (a pull request opened by `contribute`) are not retried. When the last try fails, the caller logs it with `describeError` (`lib/utils/describe-error.js`), so the reason in the error's `cause` reaches the log; see the invariant above.

**Self-hosted alternative to Gemini:** the RAG code calls Google's own SDK (`@google/genai` in `lib/rag/gemini.js`), so pointing `GEMINI_API_KEY` elsewhere does not work. Running without a third-party inference provider means replacing `gemini.js` with a client for another endpoint, for example the sibling [open-source multimodal LLM router that federates idle Macs into one OpenAI-compatible endpoint](https://ollamaherd.com) for chat and embeddings, and then rebuilding the index, since embeddings from a different model are not comparable.

**Reviewing answers:** `node scripts/eval-ask.js` (from `app/`) runs the questions in `scripts/ask-eval.json` through the same retrieve-and-generate steps as a fresh `/api/ask`, but saves and publishes nothing, and prints each answer beside what a good answer does. Run it before and after changing `lib/rag/system-prompt.md` or retrieval, and add a question when a published answer goes wrong. With `--search` it runs the same questions, and the file's unrelated queries, through search instead and prints each result's score: how search's relevance floor is calibrated. Facts about the sanctuary itself (what is live, what is stored, what goes to Gemini) belong in the system prompt's "Facts About the Sanctuary Itself", which outranks older wording in the documents.
